# 智能 JVM 配置修复与优化行动文档

日期：2026-11-06。

实施阶段用户补充：不保留旧 JSON 的兼容策略；UI 切换 JVM 模式时重建完整 JVM 配置，包括手工编辑的字段。下文配置约定已按此修正，实际完成状态与验证结果见同目录《智能JVM配置修复与优化实现-20261106》。

## 1. 结论与目标

建议保留 OneLauncher 的 **16GiB 自动堆上限**，修正其被激进模式当作固定分配值的问题。采用“需求推荐、可用内存预算、实际 Java 能力、手动设置优先”四个约束生成参数。

默认策略面向 Minecraft 客户端：合理设置最大堆，保持较小初始堆，采用精简 G1 参数。ZGC 保留为可配置选择；不根据整机内存直接切换 GC，不默认附加整套 Aikar 参数。模组数量参与需求估计，但不能保证实际工作集大小。

这次改造的验收目标是修正计算错误、避免明显过量分配和不兼容参数、保留用户配置，并让计算可独立验证。源码比较无法证明某一组参数在所有机器和整合包上性能最优；GC、帧时间和推荐系数的最终优劣需要相同游戏场景下的测量。

### 2.3 官方依据：默认 G1 与 ZGC 演进

- [Oracle JDK 21 G1 调优指南](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-garbage-collector-tuning.html)：建议从 G1 默认设置开始，按需要调整最大堆与暂停目标；固定年轻代大小会限制 G1 自适应。指南也说明 `Xms=Xmx` 和 `AlwaysPreTouch` 可以减少运行期间扩堆延迟，但把工作移到启动阶段；这适合经过测量的特定场景，不应直接作为所有桌面设备的默认值。
- [JEP 439](https://openjdk.org/jeps/439)：JDK 21 引入分代 ZGC，使用 `-XX:+UseZGC -XX:+ZGenerational`。
- [JEP 474](https://openjdk.org/jeps/474)：JDK 23 默认使用分代 ZGC，`ZGenerational` 被弃用。
- [JEP 490](https://openjdk.org/jeps/490)：JDK 24 移除非分代实现，`ZGenerational` 变为 obsolete，使用时警告并忽略；不能笼统声称 JDK 24 一定因此无法启动。
- [OpenJDK 25 参数生命周期表](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/hotspot/share/runtime/arguments.cpp#L546)：仍将 `ZGenerational` 记录为 JDK 23 弃用、24 obsolete，未指定 expiration。本轮拟对所有 Java 23+ 省略该参数，避免依赖其未来何时彻底不再识别。

PCL、HMCL 和官方资料已足够支持本轮修复决策，暂不追加 BakaXL 调研。

## 4. 拟实施的内存策略

### 4.1 统一单位与采样

1. 内部计算统一使用 MiB，`-Xmx2048m` 表示 2048MiB；GiB 仅用于说明及展示，1GiB=1024MiB。
2. 从预设工厂移除硬件查询：`CreateFromMode` 只创建配置，不决定当次堆大小和实际 GC。
3. 每次启动，在生成参数前读取一次内存快照，交给纯计算函数。校验数值有限、总量为正、可用量非负且不超过总量。
4. 增加可以表达采样失败的入口；现有 `GetMemoryMetrics` 可保留兼容包装，但 JVM 计算不得把其虚构默认指标当成可信实测值。
5. 未知内存状态时，自动堆不生成猜测的 Xmx/Xms，交给 JVM 自适应并记录检测失败；此时启动器无法保证自动堆满足上述预算或 16GiB 上限，应明确标记为 JVM 默认分配。手动堆仍按明确设置处理。真实可用内存过低时走预算不足的错误路径，不与“未知”混淆。

### 4.2 可用内存预算与 16GiB 上限

以下是拟采用的初始算法；参数集中命名，后续可根据测量调节。

令 `T` 为总物理内存、`A` 为当前可用物理内存，单位均为 MiB：

- 预留量 `R = clamp(0.10 × T, 512, 2048)`，用于当前可用空间中再给系统波动、启动器与 JVM 非堆开销留余量。它不表示 JVM 非堆一定只占这个大小。
- 可预算量 `U = max(0, A - R)`。
- 分段建议值 `H = 0.8 × min(U,8192) + 0.4 × min(max(U-8192,0),8192) + 0.2 × max(U-16384,0)`。
- 64 位自动预算 `B = min(H, U, 16384)`；32 位使用更低上限 768MiB。

该递减曲线参考 HMCL；OneLauncher 保留 16GiB 上限，预留量和随后需求约束是本项目拟定策略。不会直接采用 HMCL 中“至少用总内存的 1/16 作为可用值”的规则，以免本项目在实测剩余空间很低时提高预算。

最终结果必须向下对齐，不能因四舍五入超过预算。初始建议按 128MiB 对齐；预算低于 512MiB 时，自动模式给出“可用内存不足，请关闭其他程序或明确配置内存”的错误。这个下限是启动器策略，不声称所有旧版 Minecraft 至少必须使用 512MiB。32 位场景、非常旧的游戏和显式低堆配置需要单独验证。

### 4.3 需求推荐与模式含义

参考 PCL 将“需求目标”和“可用预算”分开，但先用可读、可测试的较简单启发式：

- 普通客户端初始目标 `D = 2048MiB`。
- 有加载器的客户端初始目标 `D = 3072MiB + 8MiB × N`，`N` 为实例 `mods` 中启用的模组数。
- 保守、标准、激进的目标倍率暂定为 `0.75 / 1.0 / 1.25`。
- 自动最大堆 `Xmx = floor128(min(B, modeMultiplier × D))`，再检查最小可用策略。
- 初始堆统一保持较小：无显式 Xms 时使用 `min(Xmx,512MiB)`；不因激进模式自动令 Xms=Xmx，也不自动预触碰整个堆。

“每模组 8MiB”、2／3GiB 基础目标和倍率均为待验证的初始启发式，不能把它们宣传为经典启动器已证明的最优系数。模组数量只估计需求：一个大型模组、资源包、光影或高视距都可能比很多小模组更耗内存。用户始终可以显式调整最大堆。

从 `instance/mods` 枚举 `.jar`，旧加载器可一并支持 `.zip`、`.litemod`；不统计 `.disabled` 文件，目录不存在时视为零。避免为了计数解压全部模组。超多模组也不得突破预算和 16GiB 自动上限。

服务端调用显式传入工作负载上下文，采用同样的预算安全规则，但不凭空使用客户端模组计数。服务器的玩家数量与世界负载没有现成输入，初始需求只作为保守默认值，并保留手动配置；服务端专项调优不纳入此次性能承诺。

## 5. GC 与 JVM 参数策略

### 5.1 默认预设

新的三种预设都以 G1 为兼容基线，区域大小保留为 0，让 JVM 自适应。暂停目标初始采用 200ms；精简默认参数只包含堆配置、已确认支持的 GC 选择和必要暂停目标。

默认不附加 Aikar、NUMA、固定 SurvivorRatio、MaxTenuringThreshold、年轻代比例、固定大区域及 AlwaysPreTouch。已有字段保留，显式配置时仍可在兼容范围内使用。三种模式主要体现需求推荐差异，不通过越来越多参数来定义“激进”。

对 Java 8 的 G1 字符串去重，需要检查实际更新版本，或在无法确认时省略；不能认为所有 Java 8 构建都支持完全一样的可选参数。实验选项的解锁开关只有在确实输出了相应实验参数时添加。

### 5.2 ZGC 与其他 JVM

| 实际 Java／实现 | 拟定处理 |
| --- | --- |
| Java 8、11、17 | 新预设默认 G1；Java 8 不支持 ZGC，Java 11／17 的显式 ZGC 按实际构建及平台能力验证，Java 11 的实验选项按需解锁 |
| Java 21、22，支持 ZGC 的 HotSpot | 显式选择 ZGC 时生成 UseZGC；选择分代时添加 ZGenerational |
| Java 23+，支持 ZGC 的 HotSpot | 只生成 UseZGC，使用默认分代模式，省略 ZGenerational |
| 不支持所选 GC 的运行时 | 默认策略使用可确认的基线；用户显式要求不支持的 GC 时给出明确错误 |
| Shenandoah | 由实际发行版／能力确认后使用，不仅依赖大版本判断 |
| OpenJ9 或实现无法识别 | 默认只生成可确认的标准堆参数，让 JVM 选择 GC；不能无条件添加 HotSpot 的 -XX 参数 |

显式 ZGC、Shenandoah 或 G1 必须互斥。结构化配置多个 GC 同时开启时报告冲突，不静默用 `if/else` 选择一个；用户原始命令行中的 GC 选择优先于自动预设。

不添加 `IgnoreUnrecognizedVMOptions` 来掩盖错误，也不把紧凑对象头等新特性自动扩展到本轮默认策略中。Aikar 的每个可选参数按实际运行时支持处理，不未经核实声称某个选项已被新版 Java 删除。

### 5.3 检查实际 Java

在生成参数前固定当次 Java 可执行文件路径；读取该运行时的 `release` 信息，必要时执行有超时的 `java -XshowSettings:properties -version`，获取版本、位数和 VM 实现。PATH 回退必须解析实际命中的可执行文件，不能用 Minecraft 元数据要求的大版本冒充实际版本。

检测结果按绝对路径及文件修改时间缓存；同一运行时并发检测合并，失败不无限重试。检测进程使用 ArgumentList、重定向并同时读取输出和错误输出，接受取消，建议 3 秒超时，超时后终止并释放进程。

`release` 和版本输出只用于识别运行时，不能单独证明发行版包含 ZGC／Shenandoah。对无法从已确认支持规则确定的显式选择，必要时用所选 GC 参数、专用小堆和 `-version` 做有限能力探测；实验选项按已知版本规则解锁。能力结果同样缓存，区分“不支持”和“检测失败”，限制探测总耗时，不使用正式游戏堆大小。若配置的是 `javaw.exe`，检测可使用同目录的 `java.exe`，同时核对它们属于同一个运行时，不能悄悄改用 PATH 中另一个 Java。

不能确认运行时能力时只输出保守、可确认的参数，并保留诊断原因。不会为 JVM 参数调优自动下载或升级 Java，也不改变 Minecraft／加载器原有 Java 选择规则。

## 6. 用户配置与参数合并

1. 不增加旧 JSON 迁移或字段合并逻辑；当前配置中“0 表示自动”的堆约定继续使用。
2. 新预设在新配置创建、用户实际重新选择模式时应用。切换时完整替换 JVM 配置对象，包括手动编辑的字段，不保留旧预设的定制值；不重置账户、下载等无关配置。
3. 设置页初始化仅加载选择状态，不调用重建预设／保存逻辑。用户主动选择预设时再保存，保存失败通过现有错误处理反馈并恢复可见状态。
4. 显式 Xmx 不受 16GiB 自动上限截断；显式 Xms 必须为正且不超过最终 Xmx。负值、无效单位和 Xms>Xmx 给出错误，不悄悄改写。只设置 Xms 时，自动 Xmx 至少容纳该值，但不能突破自动预算；无法满足则报错。
5. 用户原始 JVM 参数优先于结构化设置及自动默认值。识别其中的 `-Xmx`、`-Xms`（含对应的 `-XX:MaxHeapSize`／`InitialHeapSize` 别名）和 GC 家族，以避免自动参数重复；其他参数、引号及路径保留原有意义。
6. 在最终主类之前合并版本、加载器、自动及用户 JVM 参数，包含 `SetCommandArgs` 中必须留在命令行的参数。堆／GC 选择优先级明确为：用户原始参数 > 结构化显式字段 > 加载器参数 > 版本参数 > 自动默认值；先确定生效来源，再校验该来源，避免被覆盖的设置导致错误。同一来源的重复堆值按 JVM 最后一个值生效的语义处理，再校验最终 Xms/Xmx；同一来源同时启用多个互斥 GC 则报告冲突。仅处理这些已知家族，不顺便删除模块参数、javaagent、类路径、natives 或日志修复参数。
7. `OptimizationMode.None` 不生成启动器优化参数；服务端调用也遵循这一约定。版本与加载器本来需要的 JVM 参数照常保留。
8. 输出简明诊断：内存检测状态、自动预算、推荐需求、实际堆值、运行时版本及 GC。不得在诊断中输出账户令牌或完整敏感启动命令。

## 9. 验证方案与通过条件

### 9.1 离线算法和配置检查

- 总内存覆盖 4／8／16／32／64GiB，以及相同总量下不同可用量。
- 边界覆盖 8GiB、16GiB 分段点、16GiB 自动封顶、32 位限制、可用量小于预留、零、负数、NaN 和无穷值。
- 三种模式均满足自动预算约束；不把“最低堆”强行抬到超预算；同等条件下增加可用内存不降低自动推荐。
- 模组数量覆盖 0／100／300／2000，目录缺失、禁用文件、不同扩展名和读目录失败；计数不能触发整包解压。
- 手工 Xmx、手工 Xms、只设置 Xms、超过 16GiB 的显式堆、无效单位、Xms>Xmx、重复堆参数、互斥 GC 及 None。
- 用当前 JSON 源生成上下文验证 UI 切换后手工 JVM 字段全部重置；新预设没有硬件采样副作用；设置页构造不重建 JVM 预设。
- 模拟 release 与进程输出，覆盖实际 Java 与元数据要求不同、PATH、32／64 位、未知 VM、超时、取消和缓存失效。
- 最终主类前恰好保留有效的堆／GC 选择；加载器模块参数、javaagent、natives、类路径和日志参数保持有效。

### 9.2 实际 Java 参数冒烟

有对应运行时的环境中，用生成参数加 `-version` 检查 JVM 是否接受，覆盖 Java 8（含更新号差异）、11、17、21、22、23、24、25，补充 32 位、不同 HotSpot 发行版和可用的 OpenJ9／Shenandoah 构建。

冒烟使用专用小堆，避免测试固定提交 16GiB；大堆预算只在纯计算用例验证。实际运行时缺失时明确记录未验证，不自动下载 Java。此检查证明参数可接受，不能证明 Minecraft 启动完成或性能优于旧参数。

### 9.3 构建、AOT 与性能比较

实现后在项目内执行适用的 Core、ConsoleTest 和 UI 构建，使用已有回归入口确认设置加载和启动参数链路。Windows Native AOT 使用现有 WindowsAot 发布配置；检查新增反射、动态代码、P/Invoke 和裁剪警告。新增普通类型如果需要持久化，必须同步 JSON 源生成上下文；运行时快照和策略结果不需要写入用户配置。

后续性能验证固定游戏版本、Java 构建、模组／资源、视距与世界场景，比较启动时间、峰值进程内存、GC 暂停、帧时间 P95/P99。G1 与分代 ZGC 的比较保持相同最大堆，多次运行并记录外部内存压力。真实游戏测量作为单独验收阶段，不用 `java -version` 或纯公式样例替代。

### 9.4 隔离与清理

所有测试夹具、检测替身、Java 日志、构建隔离输出和发布文件放入 `artifacts/jvm-config-<执行日期>/`。独立检查在初始化真实启动器之前分支，不访问真实账户、游戏安装目录或用户配置，也不下载游戏文件。

夹具在 finally 中清理；执行结束清理自己创建的输出目录。递归清理前确认绝对路径仍在项目本轮隔离目录内，不删除已有产物或其他任务目录。实际检查结果用文字记录在实现文档。
