# OneLauncher 项目综合分析报告（2026-11-12）

> 性质：只读分析，未改动任何代码。标注“已验证”的条目已对照源码逐行确认；“疑似”需运行或构建确认。行号以 2026-11-12 工作区快照为准。

## 一、项目概览

OneLauncher 是基于 .NET 10 + Avalonia 12.1.4 的跨平台 Minecraft 启动器，目标是 NativeAOT 发布（Windows 单文件、Linux、macOS）。解决方案由五个项目组成：`OneLauncher.Core`（后端：下载、安装、启动、账户、资源、联机、服务端）、`OneLauncher`（真正的前端：ViewModel/View/样式）、`OneLauncher.Desktop`（启动外壳，规范要求不改动）、`OneLauncher.Console`（被 Desktop 引用的命令行入口库，支持 `--quicklyPlay`、`--joinServer`、`--releaseMemory`）和 `ConsoleTest`（试验台）。

功能覆盖面相当完整：原版/Fabric/Quilt/Forge/NeoForge 安装与启动，Mojang / BMCLAPI / SkyCrystal / Olan 多源竞速下载，微软（MSAL）与 Yggdrasil/LittleSkin 外置登录，Modrinth 资源与 .mrpack 整合包，五家 Java 发行版自动获取，智能 JVM 参数，P2P 联机，服务端管理，PCL2 版本导入，推荐模组等。

从 `docs/AI_Generated` 的 76 篇文档可以看出开发节奏：10-19 完成 Forge 与 AOT 改造；10-22 进行 DefaultComponent 迁移与 VersionList 独立存储；10-23 是最密集的一天（约 30 篇，涵盖 Page/Pane 统一、任务中心、光影包、整合包回滚、主题图标、动画）；10-30～10-31 接入 SkyCrystal、修复 Avalonia 12 单文件 AOT；11-06～11-08 做智能 JVM 与推荐模组；11-12 完成目录职责迁移、clean.ps1 与 OlanException 上下文改造。项目主要由 AI 代理迭代推进，人类负责后端骨架。

## 二、整体评价

做得好的部分：JSON 几乎全部使用源生成 `JsonSerializerContext`，前端开启 `AvaloniaUseCompiledBindingsByDefault` 且所有绑定 axaml 均声明 `x:DataType`，无 ViewLocator/反射，AOT 友好度高；发布管线把 ILLink/ILC 警告当作错误，并校验 AOT 产物中未混入 CoreCLR；配置写入采用“临时文件 + 原子替换”；Forge 系列安装链路先在暂存目录按哈希校验库文件再执行处理器，是全项目最严谨的部分；Zip Slip 已通过改用 `ZipFile.ExtractToDirectory` 修复；TaskCenter 的订阅、退订与 Dispose 链完整；`.gitignore` 与根目录结构符合规范。

主要短板集中在四个方面：凭据与下载完整性安全、异步与并发的正确性、规范执行的一致性，以及工程保障（测试、CI、README）几乎缺位。架构上，Core 实际是“全局静态 + 服务定位器”（`UnitedCore.Core.*`、`Init.Download`），`Init.Initialize` 注册的 DI 容器在 Core 内并未被真正使用，`Init.cs:11` 的注释也承认耦合较重。

## 五、低优先级与代码风格

公开 API 拼写错误较多，如 `Manger`（ConfigManger/AccountManger/MinecraftServerManger/InstanceMangerService）、`VersionInfomations`、`Strategys`、`RecommededMods`、`ApplicationVersoin`、`ModOutpoter`、`DownloadInfoCreater`、`Bmlc`、`GetLibraryiesForUsing`，以及不宜出现的文件名 `SetupFucker.cs`。命名空间与目录不一致（如 `Download.cs:3`）。`InstanceMangerService.cs`、`UserModelService.cs` 是空类，`_db_.cs` 是纯注释文件。其他小问题包括：服务端自动写 `eula=true`；Quilt 实例被命名为“原版”（`GameDataManger.cs:102-108`）；`MrpackParser.cs:84` 用 `(int)` 截断文件大小；服务端进程启动后立即 Dispose 导致无法停止；`--quicklyPlay` 缺参时 FailFast；`AccountPageViewModel.cs:167` 的惰性 `Select` 不执行；VM 中硬编码颜色不随主题；全部文本硬编码中文，无 i18n；`AutomationProperties.Name` 全项目仅 8 处。

## 六、建议路线图

第一阶段（安全与崩溃，约 1～2 天）：停止把含令牌的命令写入 `LastLaunchArgs.bat`（或脱敏），把 `LaunchCommand` 改为 class 或让 `GetArguments` 返回临时路径；`XErr` 改为 `long?` 并修正错误码；为版本号比较引入容错解析；Olan 镜像改为 HTTPS 或移出 client.jar 竞速，竞速结果强制按清单 SHA1 校验；修复 `DownloadPaneViewModel` 的 async void、`PowerPlayPane` 的事件累加和 `.Result` 阻塞。

第二阶段（正确性，约 1 周）：修复 `CheckAllSha1` 信号量、RaceDownloader 超时与资源释放、分段下载改用临时文件；修复 Yggdrasil 刷新与 MSAL 共享请求头；令牌改用 DPAPI/钥匙串加密存储；为 Java 包、authlib-injector、.mrpack 和自动更新脚本加哈希校验；补齐前端异常处理与 Task.Run/任务中心规范。

第三阶段（工程保障，持续）：修复 `Publish.sh`；重写 CI，按平台使用各自 runner 与 pubxml，并加入构建 AOT 验证；新建 xUnit 测试项目，把 `agent_test` 中的回归检查迁入；在 Core 与 OneLauncher 中开启 `IsAotCompatible`；更新 README、补 LICENSE、填充 `AI_Instruction/后端设计规范.md`；执行 `git worktree prune`。第四阶段再考虑拆分 Settings/Home 大 VM、注入 TopLevel 服务以替代 `MainWindow.mainwindow`、统一重命名拼写错误（属于破坏性改动，需要人类决策）。

按照项目规范，涉及后端设计的改动（如 DI 收敛、TaskManager 线程安全、令牌存储方案）建议由人类贡献者确定方案后，再由代理配合前端适配。
